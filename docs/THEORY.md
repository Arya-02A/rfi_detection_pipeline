# Theory — AI-Powered RFI Detection with Analysis of Radio Astronomy Data

## 1. Radio Astronomy and the RFI Problem

Radio astronomy studies astronomical phenomena through radio-frequency emission. Radio observatories work with signals that can be extremely weak compared with signals produced by equipment and transmitters near Earth.

**Radio Frequency Interference (RFI)** is unwanted radio-frequency contamination that can obscure or distort the astronomical signal of interest.

The project uses a practical two-stage idea:

```text
Robust statistics → locate suspicious high-power samples
Machine learning  → describe suspicious patches using statistical features
Visualization     → make the result inspectable
```

The project report frames the system as an interpretable bridge between advanced radio-astronomy processing and student-level understanding.

## 2. GMRT Data Representation

The project works with data stored in FITS format. FITS (Flexible Image Transport System) is widely used in astronomy for scientific data plus metadata.

The analyzed file contains visibility-related information in a table. The application reads the `DATA` field and separates complex values into real and imaginary components.

For a complex value

```text
z = R + jI
```

its squared magnitude is

```text
|z|² = R² + I²
```

The project uses this quantity as **power**:

```text
Power = Real² + Imag²
```

The selected values are arranged into a 2D **waterfall** or time-frequency representation:

```text
             Frequency →
Time ↓       ┌─────────────────────────┐
             │                         │
             │      signal / RFI      │
             │                         │
             └─────────────────────────┘
```

A waterfall makes interference patterns visually inspectable.

## 3. How RFI Appears in a Waterfall

The project report uses two simplified pattern classes:

### Narrowband RFI

A signal confined to a limited range of frequencies can persist over time. In a waterfall this is often represented as a frequency-localized stripe.

Typical examples in the report include broadcast transmitters and satellite-related transmissions.

### Broadband RFI

A short-duration interference event can spread over a wider frequency range. In a time-frequency display this can look like a burst or horizontal structure.

The report gives examples such as power-related impulsive events and radar-like signals.

> These visual patterns are useful for educational interpretation, but a visual stripe alone is not proof of a specific physical source.

## 4. Robust Statistics and Median Absolute Deviation

A key idea in the detector is that ordinary standard deviation can be distorted by extreme outliers. Since RFI itself may create large outliers, the project uses the **Median Absolute Deviation (MAD)**.

For a set of values `X`,

```text
MAD = median(|X - median(X)|)
```

For approximately Gaussian-distributed noise, MAD can be converted into a standard-deviation-like scale using:

```text
σrobust = 1.4826 × MAD
```

The detector then defines:

```text
threshold = median + k × σrobust
```

where `k` is the sigma threshold. The current dashboard defaults to `k = 7` but lets the user tune it.

Finally,

```text
RFI mask = 1,  when power > threshold
           0,  otherwise
```

### Why MAD is useful here

The median and MAD are less sensitive to a small number of very large observations than the mean and standard deviation. That makes them a reasonable robust baseline for an initial outlier detector.

## 5. Patch-Based Machine Learning Dataset

A complete waterfall can be too large and too heterogeneous to feed directly into a lightweight tabular classifier. The project therefore divides it into overlapping local windows.

Current configuration:

```text
Patch height = 64
Patch width  = 64
Stride       = 32
```

Each patch receives a binary label from the robust RFI mask.

Let

```text
r = number of masked pixels / total pixels in patch
```

The current rule is:

```text
r > 0.20  → RFI
r ≤ 0.20  → Clean
```

Thus the mask generated by the statistical detector becomes the source of weak labels for the ML stage.

## 6. Normalization

The dataset builder applies z-score normalization:

```text
z = (x - μ) / (σ + ε)
```

where `μ` is the mean, `σ` the standard deviation and `ε` a small constant for numerical stability.

For a publication-quality ML pipeline, the normalization parameters should be estimated from the training set only and then reused for validation/test data.

## 7. Feature Engineering

Instead of a neural network over the raw 64×64 image, the project summarizes each patch using eight scalar features.

### Mean

Measures average signal level.

```text
mean = average(x)
```

### Standard deviation

Measures overall variability.

```text
std = sqrt(average((x - mean)²))
```

### Maximum

Captures the strongest local peak.

### Energy

The code uses the sum of squared normalized values:

```text
energy = Σ x²
```

### Skewness

Measures asymmetry in the value distribution. Strong, asymmetric excursions can increase skewness.

### Kurtosis

Measures tail/peak behavior. High kurtosis is often associated with distributions containing unusually strong peaks.

### Time-axis variance

The code estimates variation across one axis of each patch and averages the resulting variance values. This is intended to capture temporal structure.

### Frequency-axis variance

Similarly, this captures variation associated with the frequency direction.

The feature vector is therefore:

```text
[mean, std, max, energy, skew, kurtosis, time_var, freq_var]
```

## 8. Narrowband vs Broadband Heuristic

The project starts with binary labels:

```text
0 = Clean
1 = RFI
```

For patches labelled RFI, it derives a three-class scheme using the directional variances.

```text
if frequency_variance > time_variance:
    class = 1  # Narrowband
else:
    class = 2  # Broadband
```

Together:

```text
0 = Clean
1 = Narrowband
2 = Broadband
```

This is a **rule-based weak-labeling heuristic**. It is not equivalent to having expert-annotated narrowband/broadband classes. That distinction is important when documenting model accuracy.

## 9. Random Forest Classifier

A Random Forest is an ensemble of decision trees. Each tree learns a series of feature-based split rules, and the forest aggregates their decisions.

The project uses:

```text
RandomForestClassifier(
    n_estimators=100,
    random_state=42
)
```

The model is wrapped in a pipeline:

```text
StandardScaler → Random Forest
```

### Why Random Forest fits the prototype

- It works naturally with small tabular feature vectors.
- It can represent nonlinear decision boundaries.
- It is computationally lighter than many image-based neural networks.
- It exposes feature-importance information that can help demonstrate interpretability.

## 10. Feature Importance and Explainability

The dashboard exposes Random Forest `feature_importances_` values.

Conceptually, a tree becomes more useful when a feature creates a split that reduces impurity. The aggregated feature importance therefore indicates how strongly a feature contributed to the forest's learned decisions.

Important caution:

**Feature importance is not the same thing as causal explanation.**

For a stronger explainability section in future work, permutation importance or SHAP-style local explanations could be evaluated alongside domain-specific validation.

## 11. Overlay Reconstruction

The ML model predicts one class per patch, but the user wants to see the prediction in the original time-frequency coordinates.

The project therefore reconstructs an overlay:

```text
Full waterfall
     ↓
64×64 sliding patches
     ↓
Feature extraction
     ↓
Random Forest predictions
     ↓
Place each patch back on its coordinates
     ↓
Average overlapping predictions
     ↓
2D semantic overlay
```

For overlapping regions, the implementation accumulates the class values and divides by the number of covering patches.

That creates a smooth patch-derived semantic map, but because class IDs are numeric labels, the average should be interpreted as an **overlay score** rather than a probability unless the implementation is explicitly changed to average class probabilities.

## 12. RFI Percentage and Scientific Yield

The dashboard reports an RFI percentage from the binary mask and a separate class distribution from ML predictions.

These two quantities answer different questions:

### Binary mask percentage

```text
RFI pixels / total pixels × 100
```

This reflects the fraction of the detector's time-frequency grid flagged by the robust threshold.

### Model class distribution

```text
Clean patches / total predicted patches
Narrowband patches / total predicted patches
Broadband patches / total predicted patches
```

This reflects the model's patch-level output distribution.

They should not be treated as identical physical measurements.

A stronger "scientific yield" metric would define, validate and document exactly what amount of data remains scientifically usable after flagging.

## 14. Main Limitations

The current project report explicitly lists:

- not real-time;
- manual sigma tuning;
- fixed patch size;
- not yet tested on multiple telescope datasets.

The code inspection adds several reproducibility concerns that should be fixed before presenting the ML score as a rigorous benchmark:

1. normalization is performed before the train/test split;
2. the training function performs another internal split rather than evaluating the saved test set;
3. the overlay predicts on training patches rather than a freshly reconstructed full-waterfall patch sequence;
4. Narrowband/Broadband classes are heuristic labels rather than independently validated annotations.

## 15. A Better Experimental Design

A stronger next version should use:

```text
Observation A/B/C/... 
      ↓
well-defined ground-truth/weak-label protocol
      ↓
train/validation/test separation by observation
      ↓
fit preprocessing on training data only
      ↓
train model
      ↓
evaluate once on untouched observations
      ↓
accuracy + precision + recall + F1 + confusion matrix
      ↓
qualitative waterfall/overlay inspection
```

Splitting by observation rather than randomly mixing highly overlapping patches is especially important when patches come from the same long continuous observation.

## 16. Interpretation Guide

When reading the dashboard:

- **Raw waterfall:** intensity/power in time-frequency coordinates.
- **Binary mask:** locations flagged by the robust statistical detector.
- **Feature importance:** which engineered features the Random Forest used most strongly in its splits.
- **AI overlay:** patch-level class predictions mapped back to the waterfall.
- **RFI analysis:** distribution of predicted patch categories.
- **FITS explorer:** metadata and structural information about the observation file.

The report's screenshots show the intended educational flow: a raw waterfall, binary mask, dataset builder, feature importance chart, AI overlay and a final class-distribution analysis.
